# e2e/acme — the local ACME + fake-DNS rig for the custom-domain suite

Support files for `deploy/compose/compose.acme.yaml`, which layers a local certificate
authority and a fake authoritative zone on top of `compose.ci.yaml` so
`tests/10-custom-domains.test.ts` can drive the whole custom-domain flow — add a domain, publish the
records, verify, and be served on the customer's hostname over HTTPS — with no public DNS
and no real CA.

| File | What it is |
|---|---|
| `pebble-config.json` | Pebble's config with `httpPort`/`tlsPort` moved from 5002/5001 to **80/443**, because the challenge has to arrive on the ports Caddy actually listens on. |
| `pebble-root.pem` | Pebble's own `test/certs/pebble.minica.pem`, copied out of the pinned image. It signs Pebble's **ACME endpoint** certificate (`CN=localhost`, SANs `localhost` + `pebble`), so Caddy needs it as `SSL_CERT_FILE` to talk to `https://pebble:14000/dir` at all. Public test material — it is in the image and in Pebble's git history; the matching private key is deliberately **not** copied. |
| `doh-shim.mjs` | ~90 lines of `node:dns` + `node:http`: a DNS-over-HTTPS **JSON** endpoint (`application/dns-json`, the Cloudflare/Google flavour the app's `@fundroom/dns-doh` adapter speaks) in front of `pebble-challtestsrv`, which speaks only plain DNS and RFC 8484 wire-format DoH. |

## Two different roots, and only one of them is committed

`pebble-root.pem` is **not** the CA the certificates under test chain to. Pebble mints a fresh
`Pebble Root CA <hex>` and intermediate on every start and issues from those; the committed
root only covers Pebble's own HTTPS endpoint. So the test fetches the issuing root from the
management interface (`https://localhost:15000/roots/0`, verified against the committed one)
and verifies the edge's certificate against that.

Fetching it is not a workaround, it is the stronger assertion: a certificate that verifies
against a root generated by *this* Pebble process cannot be a leftover in Caddy's storage from
an earlier run. `stack:down:acme` uses `-v` for the same reason — `caddy_data` outliving the CA
that signed what is in it is exactly the stale pass worth avoiding.

## Why a shim rather than pointing `DOH_ENDPOINTS` at challtestsrv

`pebble-challtestsrv` has a `-doh` listener, but it serves `application/dns-message`
(RFC 8484). `@fundroom/dns-doh` is deliberately a *JSON* client
(`?name=…&type=…` → `{ "Status": 0, "Answer": [{ "name", "type", "data" }] }`) because that
is what 1.1.1.1 and 8.8.8.8 serve. Translating is a few lines; teaching the production
adapter a second wire format to suit a test would not be.

The shim holds **no records of its own**. It forwards every question to challtestsrv over
real DNS and renders the real answer as JSON, so the zone has exactly one source of truth:
whatever the test published through challtestsrv's management API on `:8055`. Both consumers
then read the same zone — the CA (Pebble, via `-dnsserver`) and the app (via DoH) — which is
the property that makes the test meaningful: nothing can pass verification that the CA cannot
also see.

## Quorum

`DOH_ENDPOINTS` names **one** endpoint here, so the resolver clamps its quorum to 1 and logs
`dns.doh.quorum_clamped`. `packages/config`'s cross-field rule only requires two distinct
resolvers in prod-like environments, and this stack runs `APP_ENV=test`. Listing the shim
twice under two network aliases would have satisfied the count while still being one cache —
exactly the downgrade `dedupeByHost` exists to prevent — so the honest choice is one endpoint
and a stack that is not prod-like. The two-resolver guarantee is unit-tested in
`packages/adapters/dns-doh`.
