# FundRoom on Render

`render.yaml` is a [Render Blueprint](https://render.com/docs/blueprint-spec) generated from
`deploy/platforms/source.mjs` (`pnpm gen:deploy`); do not edit it by hand.

It creates:

- **`fundroom`** — web service from the published image (`runtime: image`), `ROLES=api,web`,
  health check `/readyz`, and a **pre-deploy command** that runs the migrations once per deploy.
- **`fundroom-worker`** — background worker from the same image, `ROLES=worker`.
- **`fundroom-db`** — Render Postgres 18.
- **`fundroom-shared`** — an environment group with the settings both processes share and the
  secrets Render generates once (`generateValue: true`): the master key, the session secret and
  the `/metrics` token. Generated once, they are never regenerated by a Blueprint sync.

## Deploy

1. Create an S3-compatible bucket (Cloudflare R2, Backblaze B2, AWS S3, …) and an access key for
   it. Render has no object storage and the two services cannot share a disk, so documents go to
   the bucket (`STORAGE_DRIVER=s3`).
2. In the Render Dashboard: **New → Blueprint**, connect your fork of this repository, and set the
   Blueprint path to `deploy/render/render.yaml`.
3. Fill in the values Render asks for (the `sync: false` variables): `BASE_URL`, `MAIL_FROM`,
   `SMTP_URL`, and the bucket (`S3_BUCKET`, `S3_ENDPOINT`, `S3_ACCESS_KEY_ID`,
   `S3_SECRET_ACCESS_KEY`). You type each one once, on the web service; the worker references it.
   `BASE_URL` is `https://fundroom.onrender.com` (or whatever name Render gives the service) until
   you add your own domain — then change it to that.
4. Apply. The pre-deploy command migrates, then both services start. The first-run setup token is
   the web service's `SETUP_TOKEN` (Environment tab); open `BASE_URL` and finish setup with it.

Back up the master key from the environment group somewhere outside Render: it encrypts
workspace data keys, and a restored database is unreadable without it. For this minor release the
Blueprint generates it under its pre-rename name, `SEEDHOST_SECRET_KEY` (see the upgrade note
below); the app reads that name and `fundroom doctor` warns about it.

## Things to know

- **Paid instance types.** Render runs pre-deploy commands only on paid web services, so the
  Blueprint uses `starter` (web), `standard` (worker: document rendering needs the memory) and
  `basic-1gb` Postgres. Change `plans` in `deploy/platforms/source.mjs` and regenerate.
- **Commands.** Neither service sets `dockerCommand`: the image's ENTRYPOINT is the FundRoom CLI
  and its CMD is `serve`. Render's Docker Command and pre-deploy command *replace* the ENTRYPOINT,
  so the pre-deploy command is the full `node … cli.js migrate` invocation. The image is
  distroless (no shell); never wrap a command in `sh -c`.
- **Image updates.** Image-backed services do not redeploy when a tag moves. Pin a version tag in
  `deploy/platforms/source.mjs` (`IMAGE`) for production and trigger a manual deploy (or a deploy
  hook) to upgrade; the pre-deploy command migrates first.
- **Readiness.** `/readyz` checks Postgres, pending migrations and the queue on every call, and
  storage, mail and the renderer until each has passed once. Render uses it to gate zero-downtime
  deploys; a Postgres outage takes the web service out of rotation rather than serving errors.
- **Custom domains.** `CUSTOM_DOMAIN_DRIVER=manual`: add each customer domain to the web service
  in Render (Render issues the certificate); FundRoom verifies DNS. On-demand TLS needs Caddy in
  front, which Render does not offer — use Compose or Coolify with Caddy for that.
- **Client address.** `CLIENT_IP_HEADER=True-Client-IP`: check it once after the first deploy
  ("Client address" below).
- **Region.** Everything is created in Render's default region (Oregon). Add `region:` to all
  three resources in the generator if you need another; it cannot be changed later.

## Client address

`CLIENT_IP_HEADER=True-Client-IP` makes the app take the visitor's address from that one header,
and it feeds rate limits, audit IPs and the `ip_allowlist` access policy. Render's edge is Cloudflare, which *sets* `True-Client-IP` when the
"Add True-Client-IP header" transform is on; Render does not document that it is, nor that a
client-supplied value is overwritten (Render only states that it appends to `X-Forwarded-For`).
Check it once, after deploy, by signing in with a forged value (you@example.com is an account on
the portal):

```sh
H='True-Client-IP: 203.0.113.9'; U=https://<your-service>.onrender.com
curl -s -H "$H" -H "Origin: $U" -H 'content-type: application/json' \
  -d '{"email":"you@example.com"}' "$U/api/v1/auth/otp/start"
# enter the code from your inbox:
curl -s -c jar -H "$H" -H "Origin: $U" -H 'content-type: application/json' \
  -d '{"email":"you@example.com","code":"<code>"}' "$U/api/v1/auth/otp/verify"
curl -s -b jar -H "$H" "$U/api/v1/me/sessions"
```

The new session's `ip` must be your own address, never `203.0.113.9`. If it is `203.0.113.9`,
set `CLIENT_IP_HEADER=CF-Connecting-IP` (Cloudflare adds it to every request it forwards) and
repeat the check.

**Upgrading from a pre-FundRoom template (renamed variables):**

- `FUNDROOM_SECRET_KEY` was `SEEDHOST_SECRET_KEY`. This Blueprint still generates the key under `SEEDHOST_SECRET_KEY` for one minor release: Render generates a separate random value per variable name and an env group cannot reference another variable, so a `FUNDROOM_SECRET_KEY` entry would be a second, different key. The app reads `SEEDHOST_SECRET_KEY` (`fundroom doctor` warns), so an existing install keeps its key when you sync. Do not add `FUNDROOM_SECRET_KEY` to the env group with any other value. A later release moves the Blueprint to `FUNDROOM_SECRET_KEY`; before syncing that one, add `FUNDROOM_SECRET_KEY` to the env group with `SEEDHOST_SECRET_KEY`'s value.
